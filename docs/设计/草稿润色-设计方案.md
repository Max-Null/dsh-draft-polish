# 草稿润色（dsh-draft-polish）设计方案

> 状态：**已实施并通过真机实测**（2026-08-20，web profile @ 3080）· v1.0
> 前置参考：分形（fractal）「输入框优化-设计方案 v1.2」与「润色直连-受控例外」决策、dsh-sidebar-qa「提问带上下文」机制、社区案例 dsh-prompt-polish / dsh-input-rewriter。
> 实施期迭代（用户反馈驱动）：①client 端补 `connection` inject（Guard 拦截致渠道继承失败）；②设置页改 DSH 原生 fields 样式语言；③设置导航图标照 dsh-plugin-center settings-nav-icon 模式（sparkles mask）；④润色按钮位置改 InputBar.tsx（rightItems 移至 ContextMeter 与发送按钮之间）；⑤loading 态保留 ✨ 星星呼吸动画 + 品牌色底，移除 toast；⑥CSS 注入改幂等替换。

## 1. 背景与目标

用户在发送按钮左侧需要一个「润色」按钮：调用 LLM 把输入框里的草稿改得更通顺、更清晰，结果回填输入框，满意后再发送。不是每个人都善于组织语言，先润色再发送能显著提升提问质量。

该功能在 OC 环境（分形）已实现两轮（v1.0 走 serve 临时会话 → v1.1 直连 DeepSeek API），但 OC 机制有结构性缺陷：**serve 的并发缺陷（#21524/#32010/#35472）导致会话正在输出时，润色临时会话被 accept 却不调度，润色必然超时**——会话未输出完之前无法使用草稿润色。

DSH 的插件机制天然规避这个问题，且比 OC 更进一步：

| 能力 | OC（分形） | DSH（本方案） |
|---|---|---|
| LLM 调用通道 | 主进程直连 DeepSeek API（受控例外，自管 key） | `ctx.llm` service——复用 DSH 现有模型渠道，**零额外凭证** |
| 会话进行中可用 | 直连后才可用（v1.1 修复） | 天然可用：llm service 独立于会话调度 |
| 会话上下文 | v1.2 决策「不带历史，仅显式引用」（贵/慢/不可预期） | `ctx.sessionQuery.readSurface` 读会话 surface，按 dsh-sidebar-qa 模式压缩注入——**本次目标** |
| 草稿按会话隔离 | 需自建 useSessionDrafts（Map + 时钟 + 持久化） | 天然隔离：input machine 每会话一个 shell |
| 凭证/渠道 | 设置页单独配 API Key | 继承 DSH 模型渠道，可单独覆盖 |

### 1.1 用户意图

> 「在 OC 环境做这个机制是想加入会话上下文帮助 LLM 更好的理解用户意图……DSH 的机制似乎更适合做这个功能，可以参考 dsh-sidebar-qa 项目中提问时带上下文机制，也可以在插件社区找找有没有优秀案例」

即：**润色要带当前会话上下文**（模型理解"我在讨论什么"才能润色得贴切），并参考 dsh-sidebar-qa 的上下文压缩注入手法控制成本。

## 2. 社区案例调研结论

在 awesome-dsh-plugin 社区清单（1724 个插件）与 npm 检索中，与本功能直接相关的案例：

| 插件 | 机制 | 与本次方案差异 |
|---|---|---|
| [jinhuoooo/dsh-prompt-polish](https://github.com/jinhuoooo/dsh-prompt-polish) | 注入 `conversation.input.right`，client fetch `/dsh-prompt-polish/optimize`，host 直连 OpenAI 兼容 API（多 provider：GLM 免费/SiliconFlow/自定义），WorkBuddy 润色规则，settings.section 配置页 | **自管 API key 体系**（甚至内置他人 GLM key 作默认，安全风险）；**不带会话上下文**；不走 DSH llm service |
| feiertu/dsh-input-rewriter | 停顿 2 秒自动改写草稿（保留代码/链接/编号） | 自动触发与"手动按钮"交互哲学不同；未确认实现深度 |
| Renzic-Stone/DSH-EasyRewrite | 已发消息内联编辑 + 版本翻页 | 针对已发送消息，非草稿 |

**结论**：社区案例证明了 `conversation.input.right` 是发送按钮左侧的正确注入点，但它们的 LLM 通道（自管 key）与上下文策略（无）都不如 DSH 原生方案。本插件定位为**DSH 原生**实现：`ctx.llm` 复用现有渠道 + `ctx.sessionQuery` 带会话上下文。

## 3. 架构总览

```
┌─ client（浏览器）────────────────────────────────────────────┐
│ conversation.input.right slot（发送按钮左侧，官方座位）        │
│  PolishButton 组件                                            │
│    ├─ 读草稿：owner props input.draft（InputZone 快照）        │
│    ├─ 写回：inputActions.setDraft(text)（标准 kit 公开动作）    │
│    ├─ 点击 → fetch POST /draft-polish/api/polish              │
│    └─ busy 态 / 错误 toast / 空输入拦截                        │
└───────────────────────────────────────────────────────────────┘
                              │ HTTP（trust fence）
┌─ host（Node）────────────────────────────────────────────────┐
│ webServer 注册 /draft-polish/api 路由                          │
│  polish 方法：                                                 │
│    1. sessionQuery.readSurface(sessionId) 读会话 surface      │
│    2. extractSegments 提取 user/assistant 文本（排除噪音）      │
│    3. 上下文窗口：近期 verbatim 截断（可选背景压缩）            │
│    4. buildPolishPrompt 组装润色指令（继承分形 POLISH_PROMPT）  │
│    5. llm.stream（复用 DSH 渠道，独立于会话调度）               │
│    6. assembleText 收流 → { ok, text }                         │
│  settings 命名空间 draft-polish（provider/model/上下文/超时）   │
└───────────────────────────────────────────────────────────────┘
```

### 3.1 为什么 DSH 是更优平台（对照 OC 的根因）

分形 v1.1 决策文档记载：serve 对临时会话的 `prompt_async` 返回 204 但回合不调度（并发缺陷 #21524/#32010/#35472），当前会话 busy 时润色轮询 60s 拿不到 assistant 文本 → 必须绕开会话调度直连 API。DSH 中：

- `ctx.llm.stream` 是独立 LLM 能力，与 agent 会话调度完全解耦——**会话进行中润色天然可用**；
- `ctx.sessionQuery.readSurface` 读的是会话日志投影（只读、非阻塞、无锁）——润色期间会话继续输出不受影响；
- 润色不创建任何会话、不写入任何日志——**零污染**（与分形决策 D6' 的"无临时会话"约束一致）。

### 3.2 上下文策略（本次核心增量，参考 dsh-sidebar-qa）

dsh-sidebar-qa 的上下文注入设计（`src/summarize.ts`）：

- `extractSegments`：从 surface events 提取 `用户：xxx / 助手：xxx` 文本段，排除插件注入的 runtime-context 快照（`source.kind === 'plugin'`）、技能目录、工具/结果噪音；
- 非对称窗口：**近期 K 条 verbatim**（每段 ≤400 字符，锚定最新状态）+ **更早背景用快速模型压缩成 ≤3 句摘要**（目标/进度/未决事项）；
- 从新到旧排列，让当前进度落在模型注意力最强位置；
- 降级：压缩失败/无渠道 → 只带近期窗口，润色不中断。

本插件默认策略（成本优先的轻量版）：

| 配置项 | 默认 | 说明 |
|---|---|---|
| `contextEnabled` | true | 总开关（用户明确要求带上下文） |
| `recentWindowMessages` | 4 | 近期 verbatim 条数，每段 ≤400 字符 |
| `backgroundEnabled` | false | 是否用快速模型把更早背景压成摘要（默认关：润色是短任务，近期 4 条已够理解意图；开则多一次快速调用） |
| `backgroundWindowMessages` | 12 | 背景压缩窗口（backgroundEnabled 时生效） |

上下文块注入格式（继承 dsh-sidebar-qa 的结构，prompt 中明确「仅作背景理解，不要引用到输出中」）：

```
【会话上下文】
用户：<最新草稿之前的最新用户消息截断>
助手：<最近回复截断>
...

【待润色草稿】
<草稿原文>
```

注意：**草稿本身不参与上下文窗口**（它是待润色主体，单独放在最末、注意力最强位置）。

## 4. 润色指令（继承分形 POLISH_PROMPT）

继承分形 `buildPolishPrompt` 的已验证指令骨架（v1.1 直连版，实测打磨过），要点：

1. 中文写作助手角色定位；**直接输出优化后的消息**，不要任何解释、前缀、引号（防污染输入框）；
2. 忠实原意：不增删事实、不改变语气/立场，修通顺与清晰度；
3. 保留代码/链接/文件路径等原样（社区 dsh-input-rewriter 同款经验）；
4. 长度约束：不显著拉长原文；
5. 分指令/提问/普通文本三类微调（社区 dsh-prompt-polish 的 WorkBuddy 分类思路）；
6. 上下文块在前、草稿在后；`temperature: 0.3` 低随机性保原意。

## 5. 数据流与交互

### 5.1 正常流程

1. 用户输入草稿（非空），点发送按钮左侧的 ✨ 润色按钮；
2. client 组装 `POST /draft-polish/api/polish`，body `{ sessionId, text }`（provider/model 可选覆盖，默认走配置）；
3. host：trust fence 校验 → readSurface 读上下文 → 组装指令 → `llm.stream`（AbortSignal.timeout，默认 30s）→ 返回 `{ ok: true, text: 润色结果 }`；
4. client `inputActions.setDraft(润色结果)` 回填输入框 + toast「已润色」；
5. 用户检查润色结果，满意后发送（发送按钮不受影响）。

### 5.2 异常分支

| 场景 | 处理 |
|---|---|
| 草稿为空 | 按钮禁用（视觉），点击无效果 |
| 润色中重复点击 | busy 态禁用按钮（spinner），防重入 |
| LLM 超时（默认 30s） | 错误 toast「润色超时」，草稿保留 |
| 无可用模型渠道 | 错误 toast「未配置模型渠道」 |
| 上下文读取失败 | 降级：只润色草稿本身，不中断（dsh-sidebar-qa 降级哲学） |
| 背景压缩失败 | 同上，只带近期窗口 |
| 润色期间切换会话 | DSH input machine 每会话独立 shell：结果写回**发起会话**的 shell（与分形 v1.2 D20 跨会话写回同目标，但由平台天然保证，无需自建 pendingPolish 协调） |
| 润色期间会话删除 | setDraft 写回已释放的 shell 为无害 no-op（平台语义） |

### 5.3 UI 细节

- 按钮 28×28 圆形，sparkle 图标（复用社区 dsh-prompt-polish 的成熟视觉），hover 高亮，主题变量 `--dsw-alias-*` 适配深浅色；
- loading 态：图标旋转 + 禁用；
- toast：错误/成功提示 2s 自动消失；
- 无障碍：`aria-label`「润色」。

## 6. 配置（settings 命名空间 `draft-polish`）

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `provider` | string | '' | 润色模型渠道；'' = 继承当前会话渠道（client 解析后传入） |
| `model` | string | 'deepseek-v4-flash' | 润色模型 |
| `reasoningEffort` | 'off' \| 'high' \| 'max' | 'off' | 思考强度（润色用 off 最快） |
| `budgetTokens` | number | 512 | 输出 token 预算 |
| `temperature` | number | 0.3 | 低随机性保原意 |
| `timeoutMs` | number | 30000 | 超时兜底 |
| `contextEnabled` | boolean | true | 是否带会话上下文 |
| `recentWindowMessages` | number | 4 | 近期 verbatim 条数 |
| `backgroundEnabled` | boolean | false | 是否压缩更早背景 |
| `backgroundWindowMessages` | number | 12 | 背景压缩窗口 |
| `backgroundBudgetTokens` | number | 160 | 背景摘要输出预算 |

注册防御性：settings service 缺失/拒绝时回退 DEFAULTS（dsh-sidebar-qa 模式）。设置 UI 走 `settings.section` 注册（社区案例同款入口）。

## 7. 安全

- 路由挂 trust fence（复用 dsh-sidebar-qa `isTrustedApiRequest`：Host-header loopback / connection row trustedHosts + sec-fetch-site/origin 检查）——DNS-rebinding/跨站防御；
- 凭证零新增：LLM 走 DSH 现有渠道，**不自管 API key**（社区案例内置他人 key 的做法明确不采用）；
- 参数校验：`text` 非空字符串、`sessionId` 字符串、长度上限（输入 ≤4000 字符，继承分形）。

## 10. 风险与边界

| 风险 | 等级 | 缓解 |
|---|---|---|
| 上下文注入偏离草稿原意 | 中 | 上下文块明确「仅背景理解」；contextEnabled 可关；草稿在最末注意力最强位 |
| 润色输出含解释文字污染输入框 | 中 | 指令硬约束「直接输出」；继承分形实测打磨过的 prompt |
| 会话上下文含敏感信息被发送给模型 | 低 | 用户显式点击才触发；与分形同款取舍（显式引用/显式触发） |
| 长上下文成本 | 低 | 默认仅近期 4 条 ×400 字符；背景压缩默认关 |
| 与既有 input.right 插件冲突 | 低 | list kind 可并存；id 唯一 |

## 11. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 新插件 `@max-null/dsh-draft-polish`，host + client 双半端 | 复用 SSiD 全家桶发布/归档体系；功能独立可裁剪 |
| D2 | LLM 走 `ctx.llm.stream`，不自管 API key | 复用用户现有渠道、零凭证、会话进行中可用；社区案例自管 key（含内置他人 key）不采用 |
| D3 | 上下文默认开启（近期 verbatim），背景压缩默认关 | 用户明确要带上下文；轻量成本优先，开关可调 |
| D4 | 注入 `conversation.input.right` | 官方契约明确定位「发送按钮左侧」；社区案例验证可行 |
| D5 | 写回用标准 kit `inputActions.setDraft` | 官方公开写路径；比社区 shell 私有路径更规范 |
| D6 | 复用 dsh-sidebar-qa 的 trust fence / settings / 压缩纯函数（拷贝实现） | 成熟验证过的实现；避免跨包依赖（插件间不互相 import） |
